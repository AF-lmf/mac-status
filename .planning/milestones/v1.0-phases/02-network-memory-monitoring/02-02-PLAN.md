<objective>
**Phase Goal (continued from Plan 02-01):**
**As a** macOS power user, **I want to** see real-time memory usage (used/total) in the menu bar alongside CPU and network rates, **so that** I can monitor RAM pressure at a glance without opening Activity Monitor.

**Plan 02-02 delivers:** A complete memory monitoring vertical slice — from `host_statistics64(HOST_VM_INFO64)` page statistics through the standard macOS "used" formula to a visible `NSStatusItem` displaying "MEM 8.2G/16G". Total physical memory is read via `host_info(HOST_BASIC_INFO).max_mem` (never the capped `memory_size` field). Memory refreshes at 2-second intervals on a background queue.

**Purpose:** Memory is the third key metric users care about (after CPU and network). This plan extends the existing StatusBarManager and AppDelegate from Plan 02-01 to add the memory vertical slice, reusing `ByteFormatting.formatMemoryCompact()` created in Plan 02-01.

**Output:** Working memory display in the menu bar alongside existing CPU and network displays. All three metrics (CPU, network, memory) visible concurrently per Phase 2 success criterion #4.

**2. Define `final class MemoryReader: TimerReader<MemoryStats>`:**

a) **Private state:**
   - `totalSize: Double = 0` — total physical memory in bytes, set once in `setup()`

b) **`init()` calling `super.init(interval: 2.0)`** per D-10: memory refresh interval is 2 seconds (slower-changing metric than network or CPU)

c) **`override func setup()`** — read total physical memory ONCE using `host_info(HOST_BASIC_INFO)`. Use the RESEARCH.md Pattern 4 (lines 270-285):
   - Declare `var stats = host_basic_info()`
   - Set `var count = UInt32(MemoryLayout<host_basic_info_data_t>.size / MemoryLayout<integer_t>.size)`
   - Call `host_info(mach_host_self(), HOST_BASIC_INFO, ...)` with `withUnsafeMutablePointer` + `withMemoryRebound(to: integer_t.self)`
   - Guard `kerr == KERN_SUCCESS` else set `totalSize = 0` and return
   - **CRITICAL:** Use `Double(stats.max_mem)`, NEVER `stats.memory_size` — `memory_size` is capped at 2 GB (PITFALL 1 from RESEARCH.md, verified in SDK header `host_info.h` line 119 vs 127). Using `memory_size` causes "MEM 2.0G/2.0G" on a 16 GB Mac (SHOWSTOPPER BUG).

d) **`override func read()`** — use the RESEARCH.md Pattern 3 (lines 238-262) for the standard macOS "used" memory formula:
   - Declare `var stats = vm_statistics64()`
   - Set `var count = UInt32(MemoryLayout<vm_statistics64_data_t>.size / MemoryLayout<integer_t>.size)`
   - Call `host_statistics64(mach_host_self(), HOST_VM_INFO64, ...)`
   - Guard `result == KERN_SUCCESS` else `onUpdate?(nil)` and return
   - Multiply each page count by `Double(vm_page_size)` (the global extern variable — do NOT hardcode 16384):
     - `active  = Double(stats.active_count) * Double(vm_page_size)`
     - `wired   = Double(stats.wire_count) * Double(vm_page_size)`
     - `compressed = Double(stats.compressor_page_count) * Double(vm_page_size)`
     - `inactive = Double(stats.inactive_count) * Double(vm_page_size)`
     - `speculative = Double(stats.speculative_count) * Double(vm_page_size)`
     - `purgeable = Double(stats.purgeable_count) * Double(vm_page_size)`
     - `external  = Double(stats.external_page_count) * Double(vm_page_size)`
   - Compute used memory with the standard macOS formula matching Activity Monitor:
     ```swift
     let used = active + inactive + speculative + wired + compressed - purgeable - external
     let free = max(totalSize - used, 0)
     ```
   - Call `onUpdate?(MemoryStats(usedBytes: max(used, 0), totalBytes: totalSize, freeBytes: free))`

e) **Sleep/wake handling:** NOT needed for MemoryReader. Unlike NetworkReader (which has delta state that goes stale), MemoryReader reads absolute values from the kernel each cycle — no baseline to reset. The `host_statistics64` call returns current page counts regardless of sleep state.

**3. Formatting:**
Do NOT add formatting code to MemoryReader. The `formatMemoryCompact` function in `ByteFormatting.swift` (created in Plan 02-01) handles display formatting. MemoryReader's responsibility ends at producing `MemoryStats` with raw byte values.

**4. Concurrency considerations:**
- `MemoryReader` extends `TimerReader<T>` which is a non-Sendable class (same as CPUReader, NetworkReader). This is acceptable — the `[weak self]` pattern in Timer closures prevents retain cycles.
- `MemoryStats` is `Sendable` — safe to pass across actor boundaries from background queue to main thread.
- `vm_page_size` is an extern C variable — Swift 6 allows access from any context. No `nonisolated(unsafe)` needed.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Kernel → MemoryReader | `host_statistics64()` and `host_info()` return kernel-populated structs. Page counts and memory sizes are kernel-provided — treat values as untrusted until validated. |
| Mach IPC → MemoryReader | `mach_host_self()` returns the current task's host port — no privilege escalation risk, but kernel calls can fail under extreme load. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-06 | Denial of Service | `host_statistics64()` kernel call | mitigate | Guard return code against `KERN_SUCCESS`. On failure, send `nil` → StatusBarManager displays "MEM --/--". No crash, no stale data. TimerReader continues polling — next cycle retries. |
| T-02-07 | Information Disclosure | `host_basic_info.max_mem` vs `memory_size` | mitigate | **Always use `stats.max_mem`** (uint64_t, actual physical RAM). Never use `stats.memory_size` (capped at 2 GB). Incorrect field produces misleading "MEM 2.0G/2.0G" on 16+ GB Macs — user-visible information disclosure via incorrect display. |
| T-02-08 | Denial of Service | Memory used calculation: negative values from corrupted page counts | mitigate | Apply `max(used, 0)` before creating `MemoryStats`. Apply `max(totalSize - used, 0)` for free bytes. Kernel corruption producing negative page counts is extremely unlikely but cheap to guard against. |
| T-02-09 | Information Disclosure | Incorrect page size assumption | accept | `vm_page_size` is a kernel-provided extern variable read at runtime — always correct for the current architecture (16384 on Apple Silicon, 4096 on Intel). No mitigation needed beyond using the variable rather than a hardcoded constant. |
</threat_model>
