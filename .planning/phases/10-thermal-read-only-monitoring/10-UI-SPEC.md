## Spacing Scale

Declared values for new Phase 10 thermal UI use SwiftUI points and must stay within the standard spacing set. Existing dashboard container values may be preserved where already present in code, but they are legacy constraints, not new Phase 10 tokens.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4pt | Title-to-row spacing, tight label/value grouping |
| sm | 8pt | Thermal row spacing, section stack spacing, unavailable-state vertical padding |
| md | 16pt | Stable trailing value reserve and larger horizontal separation when needed |
| lg | 24pt | Reserved only for future section grouping; do not add in Phase 10 unless existing layout requires it |
| xl | 32pt | Not used in Phase 10 |
| 2xl | 48pt | Not used in Phase 10 |
| 3xl | 64pt | Not used in Phase 10 |

Legacy existing-code constraints:
- Preserve the existing `DashboardView` outer `.padding(12)` if this phase touches the surrounding container; do not introduce new 12pt spacing inside `ThermalSectionView`.
- Existing card/section inner padding may currently be `10pt` in sibling views. New thermal spacing should use `8pt` or `16pt`; only retain `10pt` if direct reuse of an existing shared helper/component forces it.
- Existing footer text size `9pt` is outside the new thermal section and must not be copied into Phase 10 rows.

Popover frame contract:
- Keep `DashboardView` width at `320pt` for Phase 10.
- Do not expand to `360-380pt` in Phase 10; that belongs to Phase 12 unless the implementation proves 320pt cannot hold the dedicated thermal section.
- New thermal section uses the same full-width card treatment as the battery section but with allowed Phase 10 spacing: prefer `.padding(8)`, `RoundedRectangle(cornerRadius: 8)`, `Color.primary.opacity(0.04)`. If an existing shared card helper enforces `10pt`, document that as a legacy reuse constraint rather than a new token.
- Thermal section placement is after the battery section when battery is visible, and before process sections. This keeps hardware/system state together before longer process lists.

## Typography

Phase 10 declares exactly three text sizes and two weights for new UI.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body/value | 13pt (`.body`) | medium (500) | 1.3 |
| Row label/value | 12pt (`.caption`) | regular (400) | 1.3 |
| Micro/help/unavailable | 11pt (`.caption2`) | regular (400) | 1.3 |

Usage:
- Section title `散热`: `.font(.caption)`, `.foregroundStyle(.secondary)`.
- Primary summary value: `.font(.system(.body, design: .monospaced))`, `.fontWeight(.medium)`.
- Rows: labels use `.caption` secondary; trailing values use `.system(.caption, design: .monospaced)` secondary.
- Temperature numbers must use monospaced digits and right alignment.
- Do not introduce large display type, hero text, custom fonts, animated counters, or bold warnings in Phase 10.

## Color

Use system dynamic colors so the popover remains correct in Light/Dark Mode and accessibility appearances.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `NSColor.windowBackgroundColor` / SwiftUI default popover background | Popover base surface |
| Secondary (30%) | `Color.primary.opacity(0.04)` | Thermal section card background, matching existing cards |
| Accent (10%) | `Color.accentColor` | Settings toggle focus/interactive affordance only; no thermal value should be accent-colored by default |
| Warning | existing system orange (`#FF9500` equivalent) | Thermal state `.serious` and future threshold warning text only |
| Destructive | existing system red (`#FF3B30` equivalent) | Thermal state `.critical`; destructive actions only, none introduced in Phase 10 |

Accent reserved for: Settings controls already styled by macOS, existing accent buttons such as "恢复默认" in settings, and keyboard focus rings. It is not reserved for all interactive elements and must not be used to make normal thermal readings look actionable.

Thermal semantic color contract:
- `.nominal`: primary/default foreground, label `正常`.
- `.fair`: primary/default foreground, label `偏热`.
- `.serious`: warning/orange foreground, label `严重`.
- `.critical`: destructive/red foreground, label `临界`.
- Unknown or unavailable: secondary foreground, label `未知` or `—`.

Temperature values remain default/secondary unless Phase 10 has a clear semantic state from `ProcessInfo.thermalState`; do not invent numeric color thresholds from ambiguous sensors.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | none - Phase 10 adds no action CTA in the popover |
| Settings toggle | `散热区块` |
| Popover section title | `散热` |
| Primary temperature row | `CPU/SoC` |
| Thermal state row | `系统状态` |
| GPU row | `GPU` |
| Battery row | `电池` |
| Empty/unavailable heading | no heading; keep stable rows and show `N/A` or `—` inline |
| Empty/unavailable body | no body text; missing sensors are normal and quiet |
| Error state | no popup; inline values remain `N/A` or `—` and the section stays rendered if enabled |
| Destructive confirmation | none - Phase 10 has no destructive action |

Value strings:
- Trusted temperature: integer Celsius with no decimal, e.g. `58°C`.
- Explicitly unavailable temperature: `N/A`.
- Non-temperature optional fields or not-yet-meaningful values: `—`.
- Thermal state labels: `正常`, `偏热`, `严重`, `临界`, `未知`.
- Do not show raw SMC keys, source confidence labels, "hottest", "package", "die", "proximity", or `GPU?` in the end-user UI for Phase 10.
- If the primary CPU/SoC sensor is not explicitly trusted, show `CPU/SoC N/A`; do not relabel another sensor as CPU/SoC.

## Phase 10 Popover Contract

### Section Structure

Add one dedicated full-width thermal section gated by `SettingsManager.showThermalSection`.

Required visual order inside the section:

1. Header row:
   - Left: `散热`
   - Right: primary summary, formatted as `CPU/SoC 58°C` or `CPU/SoC N/A`
2. Stable rows:
   - `系统状态` -> `正常` / `偏热` / `严重` / `临界` / `未知`
   - `GPU` -> `58°C` or `N/A`
   - `电池` -> `34°C` or `N/A`

SSD row:
- Omit by default in Phase 10.
- Only add a stable `SSD` row if implementation discovers an existing reliable no-dependency, no-shell-out path already present in the project.
- If added, the row must use the same stable `value or N/A` contract and must not trigger a width change.

### Layout Mechanics

- Use the existing battery row pattern: `HStack { Text(label); Spacer(); Text(value) }`.
- All trailing values must be right aligned and monospaced.
- Reserve enough trailing value width for `100°C`, `N/A`, and `临界`.
- Rows owned by Phase 10 remain stable across refresh ticks. They must not appear/disappear due to transient read failures.
- Keep row spacing at `8pt` inside the section.
- No charts, sparklines, progress bars, disclosure panels, popovers-inside-popover, or scrolling subareas in Phase 10.

### Unavailable and Failure States

Unavailable is a normal state, not an error state.

| Condition | UI Result |
|-----------|-----------|
| Primary CPU/SoC sensor untrusted or unreadable | Header summary `CPU/SoC N/A`; row remains stable |
| `ProcessInfo.thermalState` unavailable or unknown | `系统状态 —` or `系统状态 未知` |
| GPU temperature unavailable | `GPU N/A` |
| Battery temperature unavailable, no battery, or battery API unreadable | `电池 N/A` |
| All temperature sensors unavailable but thermal state readable | Section remains visible with `CPU/SoC N/A` and thermal state value |
| All values unavailable | Section remains visible when enabled; values show `N/A`/`—`; no modal, alert, or red error card |

Do not cache a previous successful temperature as current after a failed read. The next rendered snapshot must reflect unavailable current data as `N/A`.

## Settings Contract

Add one toggle in `SettingsView` under the existing `弹窗区块` section.

| Setting | Contract |
|---------|----------|
| User-visible label | `散热区块` |
| Storage key | `showThermalSection` |
| Default | `true` |
| Persistence | `UserDefaults`, matching `showBatterySection` and `showProcessSection` |
| Notification | Setter posts `.settingsDidChange` with the changed key |
| Runtime behavior | Toggling applies live through SwiftUI observation and existing settings refresh behavior; no relaunch |

Behavior:
- When `showThermalSection == true`, render the thermal section even when readings are `N/A`.
- When `showThermalSection == false`, hide the whole thermal section and preserve other sections unchanged.
- Do not add a status-bar metric toggle, thermal threshold controls, alert rules, or fan-control setting in Phase 10.

## Accessibility Contract

- Preserve native SwiftUI controls and system text colors for VoiceOver, Dark Mode, and increased contrast.
- Add accessibility labels for the section and values when creating a dedicated `ThermalSectionView`:
  - Section: `散热信息`
  - Primary value: `CPU 或 SoC 温度 58 摄氏度` or `CPU 或 SoC 温度不可用`
  - Thermal state: `系统散热状态 正常` / `偏热` / `严重` / `临界`
- Temperature values should be readable as Celsius, not just a symbol-only glyph.
- Settings toggle must expose the label `散热区块` through the native `Toggle`.
- Do not rely on color alone for thermal state; the textual state label is mandatory.

---

## Interaction Contract

- Phase 10 popover thermal UI is read-only.
- There are no buttons, sliders, steppers, menus, drilldowns, or row click actions inside the thermal section.
- Refresh follows the existing collector refresh interval. The UI must not add a separate visible loading spinner for thermal values.
- Closing/reopening the popover must not reset readings beyond the normal collector state.
- Settings changes apply live and do not force a fresh SMC read solely because the toggle changed.

---

## Must Not Change in Phase 10

- Do not add fan RPM rows, fan count, fan labels, fan modes, fan capability status, manual controls, or `恢复自动`.
- Do not add any SMC write path, helper install flow, privileged prompt, XPC service, fan force-mode state, or raw SMC browser.
- Do not add a menu-bar thermal metric or alter `metricOrder` / `enabledMetrics` in Phase 10.
- Do not persist thermal samples to SQLite, history, charts, or `MetricSample`.
- Do not add notifications, warning alerts, user-facing error popups, or thermal threshold settings.
- Do not expand the popover width unless implementation proves the Phase 10 section cannot fit at 320pt; if expanded, record the rationale for Phase 12.
- Do not make secondary sensors replace or rename the primary CPU/SoC row.
- Do not show ambiguous labels that imply certainty, such as `CPU` for a package/proximity/hottest sensor whose meaning is not confirmed.
